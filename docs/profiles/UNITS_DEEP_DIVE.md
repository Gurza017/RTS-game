# Паспорта юнитов — глубокий разбор (сводный реестр, 28.09.2026)

Точка входа к доказательной базе поюнитного аудита (план 28.09.2026: этапы
1-4 оптимизации ядра → тотальный аудит по родам войск). Собирается из трёх
источников и пополняется по мере прохождения этапов:

- **`UNITS_ANATOMY_DRAFT.md`** — анатомия тика по коду: диспетчер, «ведомые
  ядром», запросы за тик по состояниям (куда уходят: GDScript / C# / движок,
  как часто), таймеры, радиусы и хитбоксы по классам с `файл:строка`.
- **`UNITS_RETRO_DRAFT.md`** — ретроспектива прогонов и партий: мкс/тик и
  худшие тики по родам (Four d0/d1, full4k, VisAb), 30 аномалий с источником
  и статусом, срезы телеметрии трёх партий при FPS < 30, открытые вопросы.
- Этот файл — сводка, ход этапов и таблица «что уже подтверждено замером».

### Этап 3 — пики (в работе, 28.09.2026)

**Честный бюджет кадра** (Four, фоновое окно, после этапа 1, ~3900 живых в
бою): 26 мс = GameManager-физика (`gm_physics`, весь колбэк) 13.6 +
GameManager-логика (`gm_process`) 2.6 + ИИ/туман/HUD/Main 2.7 + рендер
(GPU 2.7-4.4 + подача 1) ≈ 4 + движок/GC/`_process` прочих узлов ≈ 3.5.
Проверено выключением: PhysicsServer3D — 0; `_process` 3779 узлов мира — ~2 мс;
`top_level` у 5200 невидимых детей бойцов — 0. Мониторы `TIME_*` движка для
раскладки не годятся (в сумме больше стены; `TIME_PROCESS` включает рендер).
**Вывод: кадр — это тик армии; 60 FPS на 4000 требует физколбэк ≤ 7 мс.**

Причины пиков (разведка расписаний по коду): сроки коридора (200 мс), связки
боя (400), радаров (500) и сверки знамён (1 с) отсчитывались заново ОТ `now`
— после провала кадра все отряды получали срок от одного момента и дальше
срабатывали одним кадром (эхо); монахи (40) сканировали в один кадр каждые
1.2 с (`_scan_t` стартовал с нуля у всех); `_sweep_reform` судил все отряды
одним кадром раз в 0.3 с, а `close_ranks` был O(n²) (10⁴ чтений
`global_position` на отряд в 100 человек).

| правка (ручка `phase_keep`) | результат (VisAb, A/B) |
|---|---|
| срок = прошлый срок + TTL (коридор, связка, радары), фазы монахов, знамёна по фазе отряда | p95 53.5 → 51.3, p99 64.5 → 60.0, худший 69.5 → 66.4 мс; среднее без изменений |
| обход смыкания порциями (срез отрядов за кадр) + `close_ranks` O(n·m) с предвычисленными точками | замер идёт |

Кандидаты дальше: разброс кулдауна при взводе дрёмы и фаза `_retarget_timer`
после гибели цели (все ATTACKING входят в автомат одним кадром — `process_attack`
13-17 мс пиком), очередь отложенных `squad_close_ranks` со слиянием по отряду,
частичный сброс кэша навигации (`nav_route` 7.9 мс пиком после полного сброса).

### Этап 2 — коридор отряда в ядро (28.09.2026) — ЗАКРЫТ

Ручка `perf_config.squad_index_core`. Ядро ведёт **индекс строк отряда**
(`_sqNext/_sqPrev/_sqHead`, `SetSquad`/`Release` держат список) и **колонку
ряда** `_rank`; один вызов `ArmyCore.SquadRecalc(sid, …)` заменяет GDScript-обход
состава (`cor_harvest`), `SquadCorridor`, `SquadRanks` с раздачей ряда всему
составу и обход на сон. Ответ — плоский `PackedFloat32Array`: заголовок (n,
центр, габарит, дальность внимания, фракция, чисто ли от стволов/чужих, счётчики),
затем строки состава, пары (строка, ряд) **только изменившихся**, спящие (будить)
и кандидаты на сон (`FTickOn && !FTickAlways && !FDormant && IDLE && без цели`).
В GDScript остались: направление рядов (словари отряда), раздача `_clear_*` по
смене ответа, запись `_live_rank` изменившимся, подзыв сплочённости и само
решение о сне по полям бойца (`_squad_sleep_decide_rows`). Ворота личного скана
ряда (`Unit._update_live_rank`) — отрядная метка `sq["rank_ms"]`
(`GameManager.squad_rank_fresh`); личный скан и линия соприкосновения пишут
колонку ядра (`army.set_rank`), иначе ядро не увидит смену.

| замер (VisAb, A/B чередованием, раунды 2-4) | физтик, мс | кадр логики | p99 / худший, мс |
|---|---|---|---|
| прогон 1 | 22.69 → 22.21 (−0.48) | 4.82 → 4.74 | 62.1 → 59.4 / 70.4 → 63.9 |
| прогон 2 | 20.83 → 20.66 (−0.17) | 4.83 → 4.89 | 58.7 → 56.3 / 65.4 → 62.4 |

**Вывод:** честная цена GDScript-хвоста коридора — 0.2-0.5 мс физтика (профиль
обещал 1.1-1.5: завышение измерителя, как и предупреждает CLAUDE.md), пики p99
стабильно −2.4…−2.7 мс. Оставлено включённым. Это ЧЕТВЁРТЫЙ замер закона «смена
языка окупается только у однородной пакетной работы»: обход состава и ряды —
однородны, но их и было немного.

### Этап 4 — частота решений боя в контакте (28.09.2026) — ЗАКРЫТ

Ручка `perf_config.atk_half_contact`. Боец в ATTACKING, чья цель ЗА
досягаемостью, но не дальше `Unit.ATK_HALF_ZONE` 3 м (зона контакта: упёрся в
тела, доступает), помечает строку (`Unit._atk_half_set` → `ArmyCore.AtkHalfSet`,
байт `_atkHalf`, переход границы только на смене), и `TickRows` отдаёт его
GDScript-автомату через один личный тик (чётность `armyTicks / shards` против
`row / shards`) — 7.5 Гц вместо 15. Дельту пропущенного тика боец добирает сам:
`Unit._last_pf` × `Unit.tick_delta`, не больше двух тиков (после дрёмы/сна
разрыв больше — не добирается). Конница и стоящий В УПОР не затронуты: упор
ведёт дрёма, а удар после пробуждения не вправе ждать лишний такт.

**Состав GDScript-тика в свалке, строк/кадр** (новые счётчики
`ArmyCore.TickLStat`, печатает `qa_bigstand`): «удар» (в досягаемости, не
дремлет) 210-250, «контакт» (до +3 м) 160-210, «подход» (дальше) 85-125,
«покой» 90-105, прочее ~50; всего ~600-650 из ~985 живых на шард. Тики «в
досягаемости» по причинам (`perf_config.atk_why`, /с): взвёл дрёму ~2300
(один тик на каждый удар), остаток ≤ запаса `ATK_SNOOZE_SPARE` 0.15 с ~2800,
ждёт команды залпа ~300 — то есть в досягаемости лишних тиков почти нет, они
и есть цена удара.

| замер (VisAb, A/B, раунды 2-4) | физтик, мс | кадр логики | p99 / худший, мс | полутактом строк/кадр |
|---|---|---|---|---|
| критерий «стоит по факту» (прогон 2) | 20.5 → 20.7 (0) | +0.1 | 60.8 → 57.4 / 70.2 → 66.9 | 40-95 |
| вся зона контакта (прогон 3) | 20.5 → 19.6 (−0.9) | +0.6 | 58.9 → 56.5 / 66.6 → 62.7 | 60-95 |

**Вывод:** −0.9…−1.5 мс физтика и −2.5 мс p99 при ~90 пропущенных строках на
кадр (в тике 650 → 605). Условие «стоит по факту» (`moved_recently`) пробовано
и снято: в свалке разведение шевелит всех, и под него попадала половина зоны.
Расширять полутакт на «подход» (дальше 3 м, идут с навигацией) план не велит —
там удвоенный шаг меняет приход и перехват. Оставлено включённым.

### Что показали счётчики состава тика (Four, все фазы)

### Пакет 2 (`perf_config.rider_autopilot`) — конница в автопилоте до рубежа разгона

`Unit._arm_autopilot`: для `charge_range > 0` стоп автопилота —
`charge_range + RIDER_AUTOPILOT_MARGIN` 3 м (без подтягивания рядов); после
пробуждения автомат штатно взводит `_charge_ready` и разгоняется с 14 м.

**Построено и ВЫКЛЮЧЕНО по замеру** (Four detail=1, вкл / выкл): всадников
в автопилоте 335 / 369 (ср. по снимкам), свиноконница 3.10 / 3.17 (IDLE),
2.96 / 3.10 (MARCH), 3.43 / 3.45 (CLASH) мс/кадр, 28.4 / 29.0 мкс/тик — в
шуме. В партии всадник почти всегда ближе рубежа разгона (ATTACKING 390 из
446): дорог не подход, а контакт — разгон (`_charge_path` каждый тик), удар с
толчком на каждый взмах (`push_every` 1, `_apply_push` → `push_smooth`),
`_charge_impact` (худший тик 7-9 мс). Следующий кандидат по коннице —
контактная часть: толчок и разлёт как события ядра, а не GDScript-тик.

## 3a. Что уже подтверждено замером и переходит в аудит (исходный список)
